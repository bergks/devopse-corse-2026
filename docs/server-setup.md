# Конфигурация виртуальной машины devops-vm

## 1. Параметры машины
*   Объём памяти: 2048 МБ
*   Количество ядер: 2
*   Объём диска: 25 ГБ (динамически расширяемый)

## 2. Сетевые интерфейсы
*   Адаптер 1 (NAT): полученный адрес 10.0.2.15. Назначение: доступ в Интернет для обновления пакетов.
*   Адаптер 2 (Host-only): полученный адрес 192.168.56.102. Назначение: прямое подключение с хостовой системы по SSH и доступ к веб-сервисам.

## 3. Правило проброса портов
*   Порт хостовой системы: 2222
*   Порт гостевой системы: 2222 (SSH)

## 4. Учётные записи
*   `student`: принадлежит к группе `student`, аутентификация по паролю (используется для локального входа и первоначальной настройки).
*   `devops`: принадлежит к группе `sudo`, аутентификация по SSH-ключу (используется для удаленного администрирования).

## 5. Служба SSH
*   Порт: 2222
*   Изменённые директивы: `PermitRootLogin no`, `PasswordAuthentication no`, `PubkeyAuthentication yes`, `MaxAuthTries 3`, `AllowUsers devops`.
*   Расположение файла конфигурации: `/etc/ssh/sshd_config.d/99-hardening.conf`

## 6. Правила межсетевого экрана (UFW)
*   Политика по умолчанию: deny incoming, allow outgoing.
*   Разрешенные правила: 80/tcp (HTTP), 443/tcp (HTTPS), 2222/tcp (SSH с ограничением частоты LIMIT).

## 7. Снимки состояния
*   `01-clean-install` — создан после установки ОС и обновления.
*   `02-keys-configured` — создан после настройки ключевой аутентификации.
*   `03-ssh-hardened` — создан после усиления безопасности SSH.
*   `04-dns-configured` — создан после настройки локального доменного имени.
*   `04-nginx-https` — создан после настройки Nginx с HTTPS.

## 8. Веб-сервер
*   **Устанавливаемый пакет:** `nginx` (установлен из официального репозитория Ubuntu).
*   **Путь к конфигурации ресурса:** `/etc/nginx/sites-available/devops-site` (активирован через символическую ссылку в `/etc/nginx/sites-enabled/devops-site`). Стандартный ресурс `default` отключен.
*   **Каталог ресурса:** `/var/www/devops-site`.
*   **Владелец каталога ресурса:** `devops:devops`.
*   **Права на каталог ресурса:** `755` (владелец может писать, остальные — только читать и заходить).
*   **Путь к сертификату:** `/etc/ssl/certs/devops.crt`.
*   **Права на сертификат:** `644` (владелец `root:root`, доступен для чтения всем).
*   **Путь к закрытому ключу:** `/etc/ssl/private/devops.key`.
*   **Права на закрытый ключ:** `600` (владелец `root:root`, доступен только владельцу).
*   **Команда формирования самоподписанного сертификата:**
    ```bash
    sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
    -keyout /etc/ssl/private/devops.key \
    -out /etc/ssl/certs/devops.crt \
    -subj "/CN=devops.local" \
    -addext "subjectAltName=DNS:devops.local"
    ```
*   Срок действия сертификата: 365 дней.
*   Настройки TLS: разрешены протоколы TLSv1.2 и TLSv1.3. Настроен принудительный редирект с HTTP (порт 80) на HTTPS (порт 443).
*   Доставка содержимого: осуществляется утилитой rsync из локального репозитория (ветка feature/web-deploy) в каталог /var/www/devops-site/ с принудительной установкой прав (--chmod=D755,F644).

## 10. Ansible

### 10.1. Назначение

Для автоматизации настройки виртуальной машины и развёртывания приложения используется Ansible.

Конфигурация описана в виде ролей, что позволяет повторно применять настройки, устранять отклонения от заданного состояния и выполнять развёртывание без ручной установки компонентов.

### 10.2. Архитектура

Автоматизация выполняется с использованием двух узлов:

- **Управляющий узел (Control Node):** Ubuntu WSL на хостовой системе Windows. Здесь установлен Ansible и расположен Git-репозиторий.
- **Управляемый узел (Managed Node):** виртуальная машина VirtualBox с Ubuntu Server 24.04 amd64, доступная по адресу `192.168.56.102`.

Взаимодействие между узлами осуществляется по SSH через порт `22`.

Ansible работает без установки постоянного агента на управляемой машине.

### 10.3. Структура проекта

Конфигурация Ansible расположена в каталоге `ansible/` репозитория `devops-course-2026`.

Основные компоненты:

- `ansible.cfg` — параметры работы Ansible.
- `inventory/bootstrap.ini` — инвентарь для первоначальной настройки.
- `inventory/prod.ini` — инвентарь для последующего управления.
- `group_vars/all.yml` — переменные приложения.
- `requirements.yml` — зависимости Ansible Collections.
- `site.yml` — основной playbook настройки и развёртывания.
- `verify.yml` — playbook автоматического аудита.
- `roles/` — каталог ролей.

### 10.4. Inventory и учётные записи

Для управления виртуальной машиной предусмотрены два режима подключения.

**Bootstrap**

Первоначальное подключение выполняется под пользователем `student` с парольной аутентификацией.

Используется файл `inventory/bootstrap.ini`, который явно указывается при первом запуске playbook.

В процессе первоначальной настройки Ansible создаёт пользователя `devops`, устанавливает его публичный SSH-ключ и предоставляет права `sudo` без запроса пароля.

После настройки ключевой аутентификации вход по SSH с использованием пароля отключается.

**Production**

Последующие подключения выполняются под пользователем `devops` с использованием приватного SSH-ключа `~/.ssh/devops_vm`.

Для этого используется `inventory/prod.ini`, указанный в `ansible.cfg` как инвентарь по умолчанию.

Переключение между bootstrap и prod происходит между первым и последующими запусками playbook.

### 10.5. Роли Ansible

В проекте реализованы четыре роли:

| Роль | Назначение |
|---|---|
| `base` | Проверка ОС, установка системных пакетов и Docker Engine из официального репозитория |
| `ssh` | Создание пользователя `devops`, настройка SSH-ключей, sudo, SSH hardening и UFW |
| `nginx` | Установка Nginx, настройка reverse proxy и обработчиков изменения конфигурации |
| `app` | Получение Docker-образа из GHCR, запуск контейнера и проверка работоспособности приложения |

Роли выполняются последовательно в порядке, указанном в `site.yml`.

### 10.6. Параметры приложения

Docker-образ приложения хранится в GitHub Container Registry (GHCR).

Параметры развёртывания определяются в файле `group_vars/all.yml`.

- **Docker-образ:** `ghcr.io/bergks/devops-ci-app`
- **Тег:** `4702f159a204266ec9c5ab0bbae4cb2294fbc9c8`
- **Имя контейнера:** `devops-ci-app`
- **Внутренний порт приложения:** `5000`
- **Опубликованный адрес:** `127.0.0.1:5000`
- **Внешний HTTP-порт:** `80`
- **Health endpoint:** `/health`

Для развёртывания используется Docker-образ с тегом, соответствующим полному SHA коммита. Это позволяет однозначно определять используемую версию приложения.

Контейнер публикует порт только на loopback-интерфейсе виртуальной машины. Внешние HTTP-запросы принимает Nginx на порту `80` и перенаправляет их приложению.

Проверка работоспособности доступна по адресу:

`http://192.168.56.102/health`

Успешный ответ содержит HTTP-статус `200` и JSON-поле `"status": "ok"`.

### 10.7. Первоначальное развёртывание

Все команды Ansible выполняются на управляющем узле WSL.

Перейти в каталог проекта:

```bash
cd ~/devops-course-2026/ansible
```

Установить необходимые коллекции:

```bash
ansible-galaxy collection install -r requirements.yml
```

Проверить синтаксис:

```bash
ansible-playbook -i inventory/bootstrap.ini site.yml --syntax-check
```

Выполнить первоначальное развёртывание:

```bash
ansible-playbook -i inventory/bootstrap.ini site.yml --ask-pass --ask-become-pass
```

При запуске вводятся пароль пользователя `student` для SSH и пароль для выполнения команд через `sudo`.

В результате на виртуальной машине устанавливаются необходимые компоненты, настраивается SSH, запускаются Nginx и Docker-контейнер приложения.

### 10.8. Повторное применение конфигурации

После первоначальной настройки дальнейшее управление выполняется через production inventory.

Проверить подключение:

```bash
ansible all -m ping
```

Повторно применить конфигурацию:

```bash
ansible-playbook site.yml
```

При неизменном состоянии системы ожидается результат:

```text
changed=0
failed=0
```

Это подтверждает идемпотентность сценария.

Если фактическое состояние виртуальной машины отличается от описанного в Ansible, повторный запуск позволяет восстановить необходимую конфигурацию.

### 10.9. Автоматический аудит

Для проверки состояния виртуальной машины без внесения изменений используется отдельный playbook `verify.yml`.

Запуск:

```bash
ansible-playbook verify.yml
```

Аудит проверяет:

- отключение парольной аутентификации SSH;
- запрет входа под пользователем `root`;
- наличие запущенного Docker-контейнера;
- доступность приложения через `/health`;
- корректность HTTP-ответа приложения.

При успешном выполнении аудит завершается с результатом:

```text
changed=0
failed=0
```

Для проверки обнаружения неисправностей контейнер был намеренно остановлен. Аудит обнаружил отклонение и завершился ошибкой. После восстановления состояния через `site.yml` повторная проверка прошла успешно.

### 10.10. Безопасность

При автоматизации применяются следующие меры безопасности:

- SSH-аутентификация по ключу вместо пароля.
- Запрет удалённого входа под пользователем `root`.
- Ограничение входящих соединений с помощью UFW.
- Разрешение входящих TCP-соединений только на порты `22` и `80`.
- Публикация порта приложения только на `127.0.0.1`.
- Проверка конфигурации Nginx перед её применением.
- Использование фиксированной версии Docker-образа.

Приватные SSH-ключи, пароли и другие секреты не хранятся в Git-репозитории.
